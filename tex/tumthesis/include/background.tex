\section{eBPF}
\label{sec:bpf}
\ac{eBPF}, also simply known as \ac{BPF}, is a Linux-native in-kernel bytecode language and virtual machine that allows for programmable, event-driven execution across many of the kernel's subsystems. It represents an evolution from \ac{cBPF}, which also offers an in-kernel bytecode language and virtual machine but with fewer capabilities. The work flow for creating an \ac{eBPF} program typically entails writing the program in a subset of C, compiling it using a tool like LLVM, writing the user space loader program, and finally loading and attaching the program. Once a specific event occurs, the \ac{eBPF} program will subsequently be invoked. Finally, because it is a Linux-native technology, \ac{BPF} comes packaged with every kernel version since 3.18~\cite{starovoitov2014bpf}.

\subsection{Instruction Set}
\label{subsec:instruction-set}
\ac{BPF} is a general purpose \ac{RISC} architecture which can be used as a compilation target for
compiler back ends like LLVM. Typically written in a subset of C that does not allow features such as arbitrary loops, unbounded recursion, and arbitrary memory accesses, \ac{BPF} bytecode is loaded by the kernel at runtime and is later \ac{JIT} compiled into native opcodes for better performance. This approach allows the kernel to become programmable without having to cross the user-kernel space boundary. This is incredibly advantageous because it offers a flexible new way of gaining visibility into the Linux kernel as well as boosting data path performance by enabling data handling at the earliest possible stages. Moreover, BPF programs can be atomically updated at runtime without requiring a kernel restart, allowing for dynamic changes throughout a program's lifecycle.

\ac{BPF} consists of eleven 64 bit registers with 32 bit subregisters. It also contains a 512 byte stack space and a program counter. Each of the eleven registers are named \texttt{r0 - r10}, and the default operating mode is 64 bits. The 32 bit subregisters are only accessible through ALU operations. Table~\ref{tab:ebpf_registers} shows the BPF calling convention.

\begin{table}[h]
    \centering

        Register & Type     & Description \\
        \midrule
        r0       & R/W      & Exit value for BPF program. \\
        r1-r5    & R/W      & Scratch registers; hold arguments to the kernel helper function. \\
        r6-r9    & R/W      & Callee-saved scratch registers. \\
        r10      & Read-Only & Frame pointer for accessing the BPF stack. \\
        \bottomrule
    \end{tabular}

    \label{tab:ebpf_registers}

Because of the simple nature of \ac{BPF}'s calling convention, it can map directly to \texttt{x86\_64} and \texttt{arm64}, which greatly benefits the \ac{JIT} compiler given that it needs only to issue a single call instruction when placing function arguments.

\subsection{Helper Functions}
\label{subsec:helper-functions}
Depending on the hook point, a given \ac{eBPF} program will have access to a number helper functions, which provide assistance in retrieving and pushing data to the kernel. Using the registers defined in Table~\ref{tab:ebpf_registers}, a typical helper function signature will take a form similar to \texttt{u64 fn(u64 r1, u64 r2, u64 r3, u64 r4, u64 r5)}. To ensure a stable and architecture-agnostic interface, the kernel then abstracts helper functions using the macros \texttt{BPF\_CALL\_0} to \texttt{BPF\_CALL\_5}. These macros precisely define how arguments are passed from the eBPF virtual machine's registers to the kernel helper function, allowing the JIT compiler to issue direct call instructions across various CPU architectures.

\subsection{Maps}
\label{subsec:ebpf-maps}
\ac{eBPF} maps represent the way information is passed between the \ac{eBPF} program and user space application. They are key-value stores that live inside the kernel and are the data structure typically used for managing state within \ac{eBPF} programs. They also allow data to persist across multiple program executions. As seen within Figure~\ref{fig:bpf-map}, processes in user space access maps through file descriptors, and a map may also be shared between multiple processes and \ac{BPF} programs.

\subsection{Limitations}
While powerful, \ac{eBPF} isn't a silver bullet. Its capabilities remain significantly more constrained than those of a typical user space application. For example, it doesn't support function calls with six or more arguments, the strict verifier might reject a program if it can't definitively prove termination, and \ac{eBPF} programs have access to only a very limited set of helper functions and a small stack size. Finally, debugging is basic. It is currently not possible to step through an \ac{eBPF} program while it runs in the kernel, which consequently makes print debugging the most effective method. For most use cases, user space applications are still the most viable option.

\section{XDP}
\label{sec:xdp}

\ac{XDP} is a hook point situated very early in the network receive path, and it allows a loaded \ac{BPF} program to be invoked for every packet. Seen in Figure~\ref{fig:xdp-receive-path}, there are two \ac{XDP} hook points: \texttt{XDP\_DRV} and \texttt{XDP\_SKB}. The former represents the earliest point at which a packet may be processed in software, but it comes with the cost of requiring integration into the network driver. When this is not an option, \texttt{XDP\_SKB} offers a generic hook point which functions for every setup, but requires additional per-packet processing.

One stipulation to loading an \ac{XDP} program is that it may only be attached to a single queue on a specific \ac{NIC}. This is an important consideration as packet steering mechanisms like \ac{RSS} are often used to distribute different flows across the queues of a particular \ac{NIC}. Therefore, to capture all relevant traffic, it is crucial to either attach the program to every single queue or to combine the queues together using a command like \texttt{sudo ethtool -L <interface\_name> combined <number\_of\_queues>}. This directs the \ac{NIC} to use a specified number of combined receive and transmit queues.

\begin{figure}
	\centering
	\includegraphics[width=.85\linewidth]{pics/xdp_receive_path}
	\caption{XDP Hook Points}
	\label{fig:xdp-receive-path}
\end{figure}

\subsection{xdp\_md}
\label{subsec:xdp-md}
Upon entry of every single \texttt{XDP\_DRV} program, a struct \texttt{xdp\_md} is passed as an argument, providing essential information about the packet. Listing~\ref{lst:xdp-md} shows the struct's definition, which contains pointers to the beginning and end of the data as well as the index of the network interface on which the packet was received, the receive queue that handled the packet, and a metadata field where network drivers or \ac{XDP} programs can store custom information associated with the packet. As seen in Figure~\ref{fig:xdp-receive-path}, an \texttt{sk\_buff} has not yet been allocated, which is the reason for having less metadata available.

\begin{lstlisting}[caption={The xdp\_md struct}, label={lst:xdp-md}]
struct xdp_md {
	__u32 data;
	__u32 data_end;
	__u32 data_meta;
	/* Below access go through struct xdp_rxq_info */
	__u32 ingress_ifindex; /* rxq->dev->ifindex */
	__u32 rx_queue_index;  /* rxq->queue_index  */
	__u32 egress_ifindex;  /* txq->dev->ifindex */
};
\end{lstlisting}


\subsection{sk\_buff}
\label{subsec:sk-buff}
The \texttt{sk\_buff} struct, which stands for socket buffer, and whose definition can be seen in Listing~\ref{lst:sk-buff}, is the central data structure to represent a network packet as it traverses through the Linux network stack. This replaces the \texttt{xdp\_md} struct for \texttt{XDP\_SKB} programs. Created by the \ac{NIC} driver, the \texttt{sk\_buff} encapsulates the raw packet data and associated metadata such as pointers to the different protocol headers, the network interface on which the packet arrived, flags, and the length of the packet. It is used by every networking layer from the driver through to IP routing, firewalling, transport layers, and the user-space application's socket. It is designed to offer efficient in-kernel manipulation for operations like adding and stripping headers, splitting and merging packets, and supporting zero-copy. The \texttt{XDP\_SKB} hook as seen in Figure~\ref{fig:xdp-receive-path} is invoked after such an \texttt{sk\_buff} has been created.

\begin{lstlisting}[caption={The sk\_buff struct}, label={lst:sk-buff}]
type block struct {
	struct sk_buff {
        union {unnamed_union};
        __u16 inner_transport_header;
        __u16 inner_network_header;
        __u16 inner_mac_header;
        __be16 protocol;
        __u16 transport_header;
        __u16 network_header;
        __u16 mac_header;
        sk_buff_data_t tail;
        sk_buff_data_t end;
        unsigned char * head;
        unsigned char * data;
        unsigned int truesize;
        atomic_t users;
    };  
}
\end{lstlisting}

\subsection{XDP Actions}
\label{subsec:xdp-actions}
Once an \ac{eBPF} program has finished running within the XDP hook, it must return one of a few predefined actions, which then instruct the kernel on how to proceed. Table~\ref{tab:xdp_actions} shows the six different possible return codes. For instance, if a program's sole purpose is to gather statistics on packets traversing a specific queue and \ac{NIC}, \texttt{XDP\_PASS} offers a non-intrusive approach, allowing the packet to continue its journey up the network stack as usual. Alternatively, if a program aims to discard irrelevant packets, perhaps based on a packet's source IP within a \ac{DDoS} mitigation tool, \texttt{XDP\_DROP} represents one of the earliest and cheapest ways to reduce the load on the system from malicious packets. \texttt{XDP\_ABORTED} functions similarly to \texttt{XDP\_DROP} but with the additional caveat that an error has occurred. For scenarios like load balancing that distribute traffic across multiple machines, \texttt{XDP\_TX} is highly effective in that it sends the packet back out the same interface it arrived at. Finally, \texttt{XDP\_REDIRECT} can be used for layer 3 routing or in a special case, sending the raw layer 2 frame directly to user space, thereby skipping the network stack entirely.

\begin{table}[h]
    \centering
    \begin{tabular}{l p{10cm}}
        \toprule
        XDP Action & Description \\
        \midrule
        \texttt{XDP\_PASS} & Allows the packet to continue its journey through the normal network stack for further processing. \\
        \texttt{XDP\_DROP} & Immediately drops the packet at the earliest possible point, preventing it from consuming further kernel resources. \\
        \texttt{XDP\_ABORTED} & Indicates an error or that an exception occurred within the XDP program, leading to the packet being dropped. This is similar to \texttt{XDP\_DROP} but signals a problem. \\
        \texttt{XDP\_TX} & Transmits the packet back out of the same network interface it arrived on. This is often used for fast replies or packet reflection. \\
        \texttt{XDP\_REDIRECT} & Redirects the packet to a different network interface or to an \texttt{AF\_XDP} socket in user space. This enables fast packet steering. \\
        \bottomrule
    \end{tabular}
    \caption{XDP Program Return Actions}
    \label{tab:xdp_actions}
\end{table}
