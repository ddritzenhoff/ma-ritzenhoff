\chapter{Related Work}
\label{chap:related-work}
In this chapter, we provide an overview of existing literature relevant to QUIC performance analysis and optimization and describe how our work differs.

\subsubsection{QUIC Performance Improvements Using Socket Optimizations and Kernel Bypass}
\label{subsubsec:spaeth-thesis}
This thesis is thematically similar to the Master's Thesis \emph{QUIC Performance Improvements Using Socket Optimizations and Kernel Bypass}~\cite{spaeth2023}, which investigates methods to improve QUIC performance by means of patching MsQuic with \ac{DPDK} and using socket optimizations such as segmentation offloading and message batching. As a result of his experiments, Spaeth showed that the default MsQuic datapath using optimizations such as message batching (i.e. \texttt{sendmmsg(2)}) and segmentation offloading (i.e. \texttt{GRO/GSO}) was able to reach a goodput of 8254 Mbit/s, which outperformed the \ac{TCP}+\ac{TLS} reference stack. Moreover, Spaeth showed that kernel bypass with \ac{DPDK} reached a goodput of 4290 Mbit/s, which was not able to exceed the goodput of the default datapath.

This thesis differs from Spaeth's work in that it focuses on goodput measurements using \ac{XDP} rather than \ac{DPDK}. Additionally, this thesis placed an additional emphasis on latency by measuring the 'network stack' traversal time of packets using \ac{PTP} with various datapaths. One similarity between our work, however, is that both \ac{DPDK} and \ac{XDP} were not able to exceed the goodput of the default MsQuic datapath.

\subsubsection{Improving the performance of picoquic by bypassing the Linux Kernel with DPDK}
\label{subsubsec:nikita-thesis}
This thesis is also thematically similar to the Master's Thesis \emph{Improving the performance of picoquic by bypassing the Linux Kernel with DPDK}~\cite{nikita2021}, which investigates the performance increases resulting from adding DPDK to picoquic~\cite{picoquic}, a QUIC implementation written in C. From his experiements, Tyunyayev showed how \ac{DPDK} increased goodput by a factor of three relative to the default datapath in a simulated web request test when the number of cores was limited to one. With the core-contraint lifted, the performance difference between \ac{DPDK} and the default datapath reduced to 1.85x. These results, being contradictory to those by Spaeth, can be partly explained by the fact that picoquic used an unoptimized default datapath. For example, one such feature not included by picoquic was message batching (i.e. \texttt{recvmsg(2)} instead of \texttt{recvmmsg(2)}). With respect to latency, Tyunyayev also showed the \ac{DPDK} version having a 30\% lower latency over the default datapath.

Much like with Spaeth, this thesis differs from Tyunyayev's work in that it focuses on goodput measurements using \ac{XDP} rather than \ac{DPDK}. Additionally, this thesis focused on a slightly different type of latency by measuring the 'network stack' traversal time of packets using various datapaths with \ac{PTP}, rather than the time-to-first-byte of web responses as done by Tyunyayev.

\subsubsection{Accelerating QUIC with AF\_XDP}
\label{subsubsec:huang-and-zhao}
Huang and Zhao~\cite{10.1007/978-981-97-0798-0_6} investigated quic-go\footnote{https://github.com/quic-go/quic-go} by integrating \texttt{AF\_XDP} as a new datapath. They developed \texttt{XSKConn}, a Go library that replaces the standard Linux network stack datapath with an \texttt{AF\_XDP}-based alternative. Their throughput and \ac{RPS} tests demonstrated that the XDP-enabled quic-go, both with and without zerocopy, consistently handled more \ac{RPS} than the default datapath in ping-pong and file-download scenarios. Notably, with more than four clients, \texttt{XSKConn} improved RPS by over 30\% in the ping-pong tests. Furthermore, the XDP versions exhibited significantly lower CPU usage (5-50\% less) in both test cases.

This thesis diverges from Huang and Zhao's work in several key aspects. First, we focus on MsQuic, which has demonstrated superior goodput compared to quic-go~\cite{spaeth2023}. Additionally, our research uniquely measures network traversal time using \ac{PTP}, a metric not explored by Huang and Zhao. Finally, contrary to their findings, our throughput tests revealed inferior performance with \ac{XDP} compared to the default MsQuic datapath. This discrepancy could stem from Huang and Zhao's measurements being conducted on an older version of quic-go that lacked datapath optimizations like \ac{GRO}\footnote{https://github.com/quic-go/quic-go/issues/3838}, which MsQuic already included.

\subsubsection{lxin-quic}
lxin-quic~\cite{quic_lxin} is an active project bringing a majority of QUIC features into the kernel, while keeping the handshake within userspace. It establishes a new socket type \texttt{IPPROTO\_QUIC}, which operates over \ac{UDP} tunnels. Fundamentally, this approach offers a number of benefits over application-space QUIC implementations. First, it adhears itself to the standardized networking APIs by covering operations like \texttt{listen(2)}, \texttt{accept(2)}, \texttt{connect(2)}, \texttt{sendmsg(2)}, \texttt{recvmsg(2)}, \texttt{close(2)}, \texttt{get/setsockopt(2)}, and \texttt{getpeername(2)}. This makes it easier for applications using \ac{TCP} to switch over to QUIC. Another advantage is the minimization of data duplication through system calls like \texttt{sendfile(2)} as described in Subsection~\ref{subsec:quic-limitations}. Although existing outside the kernel during its development\footnote{https://github.com/lxin/quic}, lxin-quic has now been included as part of a patch set introducing the core QUIC infrastructure and subcomponents\footnote{https://lwn.net/Articles/1028932/}.

This thesis differs from lxin-quic for the clear reason that our work with MsQuic represents a fundamentally different approach at integrating QUIC, being that it exists in userspace. \ac{XDP} and \ac{DPDK} are therefore incompatible with the lxin-quic approach.
