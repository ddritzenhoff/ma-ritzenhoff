\section{Performance Improvement Potential}
\label{subsec:performance-improvement-potential}

\ac{DPDK} fundamentally achieves reduced packet I/O overhead through kernel bypass. Unlike solutions such as AF\_XDP's use of ring buffers to minimize system calls and context switches, \ac{DPDK} completely sidesteps the Linux kernel's networking stack. It moves all packet processing directly into userspace, allowing applications to communicate directly with the \ac{NIC}. This eliminates the need for frequent system calls and context switches during packet transmissions, significantly boosting performance. To further reduce latencies, \ac{DPDK} employs a \ac{NIC} polling driver model instead of an interrupt-based one and utilizes Hugetables to alleviate pressure on the Translation Lookaside Buffer and to keep related data in contiguous memory.

An in-kernel QUIC implementation offers significant advantages by providing direct access to low-level network stack primitives, such as queueing disciplines. This enables extremely granular control over network traffic, for example, and it represents a level of precision largely unavailable to userspace implementations. Furthermore, the in-kernel approach proves particularly beneficial when utilizing the \texttt{sendfile(2)} system call. As illustrated in Figure~\ref{fig:memory-bandwidth-QUIC}, \texttt{sendfile(2)} avoids costly data copies into userspace by keeping data exclusively within kernel memory, thereby reducing memory bandwidth and CPU usage.

As detailed in Subsection~\ref{subsubsec:gro}, \ac{GRO} and \ac{GSO} fundamentally reduce per-packet processing overhead. They achieve this by aggregating multiple smaller packets into larger "mega-packets" as data traverses the network stack. This aggregation effectively leads to less processing required per byte of payload data. Consequently, this optimization results in fewer system calls during data transmission and reception, thereby reducing the number of costly context switches and improving overall network efficiency.

\section{Implementation Complexity}
\label{subsec:implementation-complexity}
% this is about implementing within the quic implementation

Because \ac{DPDK} offloads all networking functionality from the kernel, integrating it as a QUIC datapath necessitates a complete re-implementation of Layer 2 and Layer 3 packet processing, alongside functionality such as checksum calculation, ARP/Neighbor resolution, and routing. Furthermore, sending and receiving packets would require direct interaction with DPDK's API, which has little overlap with the standard Linux networking API. This makes integration extremely complicated.

Implementing QUIC within the kernel moves most of the protocol's functionality there, while leaving the \ac{TLS} handshakes to userspace. This inherent split across the kernel-userspace boundary requires synchronization mechanisms such as netlink or the use of control messages with \texttt{sendmsg(2)} and \texttt{recvmsg(2)}. Additionally, an existing significant challenge for lxin-quic is its reliance on hooking into kernel functions. These functions are inherently unstable across different kernel versions, potentially leading to substantial maintenance efforts to ensure compatibility and stability across various Linux distributions and kernel updates.

A notable disadvantage of AF\_XDP is its requirement for extensive knowledge of kernel internals. Developers must have an in-depth understanding of \ac{eBPF}, \ac{XDP} hooks, and AF\_XDP-specific features such as the four ring buffers and the UMEM region. This steep learning curve, combined with historically sparse documentation and a limited number of fully-fledged examples, makes AF\_XDP integration within a QUIC implementation also challenging.

Implementing \ac{GSO} and \ac{GRO} within QUIC is comparatively straightforward. It primarily involves leveraging specific kernel socket options and system calls. Relative to the other datapaths discussed, they require minimal setup.

\section{Unwanted Side Effects}
\label{subsec:unwanted-side-effects}

A significant drawback of using \ac{DPDK} is its exclusive control over the \ac{NIC}. By detaching the \ac{NIC} from the kernel, \ac{DPDK} renders it "invisible" to the standard Linux networking tools and other applications. This is particularly problematic in single-\ac{NIC} systems, as it prevents other userspace applications from accessing the network. Furthermore, \ac{DPDK}'s hardware configurations are limited, as it only supports a specific set of \ac{NIC}s and drivers\footnote{https://core.dpdk.org/supported/\#nics}.

The appropriate size of the UMEM region within AF\_XDP is highly dependent on the system's total throughput. As detailed in Subsection \ref{subsec:spontaneous-test-failures}, reserving too small a region can lead to silent packet loss, impacting application reliability.

Bugs within an in-kernel QUIC implementation pose a much greater risk than those in a userspace implementation. An in-kernel bug can lead to a system-wide crash, affecting all running applications. Conversely, a bug in a userspace QUIC implementation would typically result in only a single application failure, limiting the scope of impact.

One notable downside to \ac{GSO} is the potential for packet bursts upon transmission. Because packets are "jumbled" together into a large frame until the very last moment in software, there are often few mechanisms to prevent these bursts as they leave the \ac{NIC}, as demonstrated by Kempf et al.~\cite{Kempf_2025}. This unmitigated bursting can lead to performance degradation.

\section{Privilege Level Usage and Deployment}
\label{subsec:bring-up-and-privelege-level-usage}

Bringing up lxin-quic requires loading it as a kernel module. Like other kernel modules, this operation necessitates root privileges or the \url{CAP\_SYS\_MODULE} capability\footnote{https://man7.org/linux/man-pages/man7/capabilities.7.html}. With respect to deployment, lxin-quic aims for smooth integration by adopting the standardized Linux socket APIs. This means applications already using the Linux socket API for \ac{TCP} can leverage the same networking system calls (e.g., \texttt{listen(2)}, \texttt{accept(2)}, \texttt{connect(2)}, \texttt{sendmsg(2)}, and \texttt{recvmsg(2)}) for QUIC. This significantly reduces the friction associated with its adoption. Finally, it's important to note that lxin-quic is currently under active development and is in an immature state, which may lead to trouble during deployment.

Because \ac{DPDK} also relies on kernel modules such as \texttt{vfio-pci}, it too requires elevated privileges for use. For deployment, Hugepage support must be enabled within the running kernel via the HUGETLBFS option\footnote{https://doc.dpdk.org/guides/linux\_gsg/sys\_reqs.html}. Once the \ac{DPDK} source code is downloaded, it is compiled, and scripts are used to bind the \ac{NIC} to \ac{DPDK}. This binding grants the application complete control over sending and receiving network traffic, after which it may begin to send traffic.

\ac{XDP} also requires higher privileges. Specifically, loading \ac{XDP} programs (of type \url{BPF\_PROG\_TYPE\_XDP}) is a privileged operation. For deployment, a library like libxdp\footnote{https://github.com/xdp-project/xdp-tools/tree/main/lib/libxdp}, which contains \ac{XDP} helper functions, may be used. At runtime, the application loads the \ac{eBPF} program into the \ac{XDP} hook, which then redirects packets to userspace. Subsequently, the application must create the AF\_XDP socket and User Memory (UMEM) region as described in Section~\ref{sec:xdp}.

\ac{GSO} and \ac{GRO} must first be enabled using a tool such as \texttt{ethtool -K}\footnote{https://man7.org/linux/man-pages/man8/ethtool.8.html}. Within the context of \ac{UDP}, the desired segment size (i.e. UDP\_SEGMENT) must then be specified with a \texttt{setsockopt} call. This allows the userspace application to send a "massive" packet through the network stack, which is subsequently split into smaller segments in software just before transmission.
