\subsection*{Topic}

QUIC~\cite{rfc9000} is a new general-purpose transport protocol, first standardized by the Internet Engineering Task Force (IETF) in 2021, which combines features from mature protocols such as TCP~\cite{rfc9293}, UDP~\cite{rfc768}, and TLS~\cite{rfc8446}. QUIC differentiates itself in that it offers secure connections by default, promises fewer round trips before data is transmitted, fixes the head-of-line blocking present with TCP, and is designed to be extensible through its user space implementations. These features have made QUIC an ideal foundation for new application-layer protocols such as Hypertext Transfer Protocol 3 (HTTP/3)~\cite{rfc9114}, which now commands 20.5\% of HTTP traffic worldwide~\cite{cloudflare2024}. This underscores the importance of optimizing QUIC’s performance as its adoption and significance continue to grow. Relatedly, previous work from Jaeger et al.~\cite{quic_on_the_highway} has shown that packet I/O is QUIC's largest bottleneck in terms of its maximum achievable throughput. The following paragraphs explore a few approaches to addressing this limitation.

EXpress Data Path (XDP) is a high performance data path in the Linux kernel based on the extended Berkeley Packet Filter (eBPF) runtime. First introduced in 2016~\cite{linux_xdp_merge_2016}, XDP works by attaching a hook into the network receive (RX) path, which can be used to handle packets at the earliest possible time, before any other work is done. With AF\_XDP, a socket type, it is also possible to send the raw layer 2 frames with XDP directly to the user space QUIC implementations. At the cost of some additional header processing, AF\_XDP allows the packets to skip the Linux network stack entirely, which adds much overhead to each packet. Moreover, a Linux kernel patch from 2023 enables Ethernet frame checksum offloading specific to AF\_XDP~\cite{fomichev2023xsk_tx_metadata}, which shifts its computation from the CPU to the Network Interface Controller (NIC), corresponding in less CPU usage.

Another approach to the packet I/O limitation is DPDK~\cite{dpdk}, a software framework providing a set of data plane libraries and NIC polling-mode drivers to offload all packet processing from kernel space into user space. The fundamental difference between XDP and DPDK is that XDP represents network stack bypass while DPDK represents kernel bypass. This allows DPDK to avoid overheads generated by context switching, copying data between kernel and user space, interrupt handling, and the Linux scheduler. However, this is accomplished at the expense of having to reimplement many of the Linux network stack features such as firewalling, traffic shaping, routing, and socket APIs.

In-kernel QUIC~\cite{quic_lxin} is yet another approach, which moves QUIC from user space into kernel space. Advantages include seamless integration with kernel subsystems, standardized socket APIs for QUIC, and reduced context switches. However, this also comes at the cost of slow update cycles due to the nature of conservative Linux kernel upgrades, which user space implementations do not suffer from.

In sum, this Master's Thesis shall investigate the performance improvements in throughput and reduced CPU usage as a result of combining AF\_XDP with QUIC and patching MsQuic to add support for Ethernet frame checksum offloading. This is done in parallel to creating a taxonomy in which we evaluate various QUIC optimizations addressing the packet I/O limitation, organizing each based on implementation complexity, performance improvement potential, and unwanted side effects.

\subsection*{Related Work}

% \todo{Explain here how this project compares to existing publications}

This thesis is thematically similar to the Master's Thesis \emph{QUIC Performance Improvements Using Socket Optimizations and Kernel Bypass}~\cite{spaeth2023}, which investigates methods to improve QUIC performance by means of patching MsQuic with DPDK and using socket optimizations such as segmentation offloading and message batching. It does not, however, investigate XDP.

This thesis is also thematically similar to the Master's Thesis \emph{Improving the performance of picoquic by bypassing the Linux
Kernel with DPDK}~\cite{nikita2021}, which investigates the performance increases from adding DPDK to picoquic~\cite{picoquic}, a QUIC implementation written in C. It does not investigate XDP.

Huang and Zhao~\cite{10.1007/978-981-97-0798-0_6} describe accelerating QUIC with AF\_XDP in quic-go. This thesis differs by focusing on the additional benefits introduced from hardware offloading with AF\_XDP in addition to the creation of a taxonomy across various QUIC optimizations. This paper also lacks scientific rigor by not providing artifacts and a way to reproduce the experiments.

Pantuza et al.~\cite{eQUIC_Gateway} increases QUIC throughput by combining it with XDP to rate limit connections. Our thesis differs by focusing on the throughput and CPU usage benefits that come from strictly combining QUIC with XDP and using checksum offloading.

lxin-quic~\cite{quic_lxin} is an active project bringing QUIC into the kernel space, which offers a different approach to XDP and DPDK at reducing packet I/O by eliminating the need for frequent context switches. This thesis will consider the work done here with respect to creating the taxonomy.

\subsection*{Approach}
In the first part, we will build MsQuic with XDP for Linux and measure goodput in client-server file download scenarios using the QUIC Interop Runner (QIR) from Jaeger et al.~\cite{quic_on_the_highway}. Documentation for XDP in MsQuic is poor, and the code is still experimental, so this is not expected to be trivial. For the analysis, we will use the performance analyzing tool perf~\cite{melo2010perf} to track CPU usage over time. This allows us to analyze the benefits from using XDP over the XDP-less MsQuic implementation. Moreover, FlameGraphs~\cite{gregg_flamegraph_2024} will build upon this data and produce complementary visuals. Finally, we will also use the QIR infrastructure to calculate the throughput achieved. This will allow us to compare the throughput per CPU usage between XDP MsQuic and non-XDP MsQuic.

Next, we patch MsQuic to use AF\_XDP metadata and TX checksum offloading, support for which was added to the Linux kernel in early 2023~\cite{fomichev2023xsk}. This will require understanding the structure of the MsQuic code and modifying the requisite components. Thereafter, we use the mlx5 driver from Mellanox, the only driver to carry support for these changes, to re-run the performance tests from part one. We expect the CPU usage decrease for the same amount of throughput.

Finally, we create a taxonomy for QUIC optimizations, organizing each based on implementation complexity, performance improvement potential, and unwanted side effects. We will use the QUIC Interop Runner to evaluate all the optimizations in the same test environment.
