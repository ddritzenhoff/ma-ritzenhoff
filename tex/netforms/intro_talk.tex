\subsection*{Topic}

QUIC \cite{rfc9000} is a new general-purpose transport protocol, first standardized by the Internet Engineering Task Force (IETF) in 2021, which combines features from mature protocols such as TCP~\cite{rfc9293}, UDP~\cite{rfc768}, and TLS~\cite{rfc8446}. QUIC differentiates itself in that it offers secure connections by default, promises fewer round trips before data is transmitted, fixes the head-of-line blocking present with TCP, and is designed to be extensible through its userspace implementations. The Hypertext Transport Protocol 3 (HTTP/3)~\cite{rfc9114}, which is the newest version of HTTP and is the most popular application-level protocol built upon QUIC, now commands 20.5\% of HTTP traffic worldwide~\cite{cloudflare2024}. Therefore, as QUIC increases in usage, it is critical to find ways to improve its performance. Previous work from Jaeger et al.~\cite{quic_on_the_highway} has shown that QUIC throughput is most impacted by packet I/O. One of the approaches to reducing this overhead is with eXpress Data Path (XDP), which is a high performance data path in the Linux kernel based on the extended Berkeley Packet Filter (eBPF) runtime. First introduced in 2016~\cite{linux_xdp_merge_2016}, XDP works by introducing a hook into the network receive (RX) path and can be used to handle packets at the earliest possible time, before any other work is done. With AF\_XDP, a socket type, it is also possible to send the raw layer 2 frames with XDP directly to the userspace QUIC implementations. At the cost of some additional header processing, AF\_XDP allows the packets to skip the Linux network stack. Moreover, to further increase performance, we may begin offloading certain QUIC protocol features. This Master's thesis shall investigate the performance improvements in throughput and reduced CPU usage as a result of combining AF\_XDP with QUIC and patching msquic to add support for Ethernet frame checksum offloading.

\subsection*{Related Work}

% \todo{Explain here how this project compares to existing publications}

This thesis is thematically similar to the Master's Thesis \emph{QUIC Performance Improvements Using Socket Optimizations and Kernel Bypass}, which investigates methods to improve QUIC performance. It does not, however, investigate XDP.

Huang and Zhao \cite{10.1007/978-981-97-0798-0_6} describe accelerating QUIC with AF\_XDP in quic-go. This thesis differs by using msquic. Additionally, this paper lacks scientific rigor by not providing artifacts and a way to reproduce the experiments.

Pantuza et al. \cite{eQUIC_Gateway} increases QUIC throughput by combining it with XDP to rate limit connections. Our thesis differs by focusing on the throughput and CPU usage benefits that come from strictly combining QUIC with XDP and using checksum offloading.

\subsection*{Approach}
In the first part, we will build msquic with XDP for Linux and measure goodput in client-server file download scenarios using the QUIC Interop Runner (QIR) from Jaeger et al.~\cite{quic_on_the_highway}. Documentation for XDP in msquic is poor, and the code is still experimental, so this is not expected to be trivial. For the analysis, we will use the performance analyzing tool perf~\cite{melo2010perf} to track CPU usage over time. This allows us to analyze the benefits from using XDP over the XDP-less msquic implementation. Moreover, FlameGraphs \cite{gregg_flamegraph_2024} will build upon this data and produce complementary visuals. Finally, we will also use the QIR infrastructure to calculate the throughput achieved. This will allow us to compare the throughput per CPU usage between XDP msquic and non-XDP msquic.

Next, we patch msquic to use AF\_XDP metadata and TX checksum offloading, support for which was added to the Linux kernel in early 2023 \cite{fomichev2023xsk}. This will require understanding the structure of the msquic code and modifying the requisite components. Thereafter, we use the mlx5 driver from Mellanox, the only driver to carry support for these changes, to re-run the performance tests from part one. We expect the CPU usage decrease for the same amount of throughput.
